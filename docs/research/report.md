# ЛР 2 — обоснование актуальности ВКР

**Тема ВКР:** Разработка и исследование подхода к безопасной автоматизации развёртывания сервисной инфраструктуры (Docker Swarm, K3s, PostgreSQL/TimescaleDB, Redis, Apache Kafka) на основе SaltStack с централизованным управлением секретами и PKI через HashiCorp Vault

**Автор или участники команды:** Зюзин Владислав (GitHub: `VladislaZyuzin`)

**Вклад каждого участника при командной работе:** работа индивидуальная; весь вклад — автор.

> Исходный материал: репозиторий `K3S_Swarm_Vault_by_Salt` — рабочая документация и состояния (states) Salt для стенда из ~12 ВМ на Ubuntu 24.04 LTS (Proxmox). Ссылки вида [N] — на список источников в разделе 2.

### Выводы по обзору

**Что уже сделано.** IaC стал стандартной практикой, инструменты (Ansible, Puppet, Chef, Salt, Terraform) хорошо описаны [3], [11], [14]. Vault широко применяется для секретов и PKI, есть промышленный опыт его интеграции с системами управления конфигурациями [12], [16]. Kafka перешла на KRaft и больше не требует ZooKeeper [8].

**Какие подходы можно использовать.** Декларативные состояния Salt с данными в pillar; хранение секретов в Vault и подтягивание их через `ext_pillar`; выпуск сертификатов узлам через Vault PKI с аутентификацией AppRole; взаимная TLS-аутентификация по принципам нулевого доверия [7].

**Какие вопросы остаются нерешёнными.**

1. Безопасность самих IaC-скриптов изучена хуже, чем преимущества подхода [1], [2]. Типовые проблемы встречаются и в исследуемом стенде: секреты в командной строке (`-passin pass:…`, `-password pass:…`) и в конфигурационных файлах, токен Vault с ручным продлением, обращение к Vault по HTTP с `verify: false`.
2. По Salt заметно меньше публикаций, чем по Ansible и Terraform, особенно по связке Salt + Vault PKI + Kafka; в основном это статьи сообществ [11], [14].
3. Нет готового воспроизводимого образца развёртывания «Swarm + K3s + PostgreSQL/TimescaleDB + Redis + Kafka» с единой схемой секретов и сертификатов, который можно проверять автоматически (идемпотентность, тесты, статический анализ).
4. Жизненный цикл версий Salt требует отдельного внимания: в стенде закреплена версия 3007.8, а 3007 относится к STS-ветке; в мае 2026 вышла 3008 LTS [9].

### Выводы по сравнению

**Что можно использовать.** Идеи из Ansible и Puppet: проверка кода линтерами, тестирование ролей, организация данных в иерархию [3]. Из cp-ansible — проверенный набор TLS-параметров Kafka. Из опыта Авито — осторожность с зависимостью конфигурации от доступности Vault [12].

**Какие ограничения предстоит устранить** (по результатам разбора текущего стенда):

- токен Vault выдан на год и продлевается вручную (при истечении ломается рендер pillar), в скриптах фигурирует root-токен; для связи с Vault используется HTTP и `verify: false`;
- пароли передаются в командной строке (`pass:…`) и записываются в `server.properties` открытым текстом [2];
- слушатель контроллеров Kafka работает как `PLAINTEXT`, TLS защищает только брокеры;
- мастера синхронизируются раз в сутки cron+rsync, возможен дрейф между ними;
- в Kubernetes Dashboard включён `--enable-skip-login` и привязка `cluster-admin`;
- есть опечатки и рассогласования имён (`k3s_test` и `k3s_check`, ссылки на несуществующие состояния), что показывает отсутствие автоматических проверок;
- закреплена версия Salt 3007.8 (STS) вместо поддерживаемой LTS-ветки [9].

## 4. Итоги

**Итоговая тема ВКР:** Разработка и исследование подхода к безопасной автоматизации развёртывания сервисной инфраструктуры (Docker Swarm, K3s, PostgreSQL/TimescaleDB, Redis, Apache Kafka) на основе SaltStack с централизованным управлением секретами и PKI через HashiCorp Vault

**УДК для тезиса:** 004.4:004.056

**Ключевые слова:** инфраструктура как код, SaltStack, HashiCorp Vault, PKI, управление секретами, Apache Kafka, KRaft, Kubernetes, K3s, Docker Swarm, отказоустойчивость, DevSecOps

### Актуальность исследования

1. **IaC стал стандартом, а его безопасность — слабое место.** Исследования показывают, что IaC-скрипты содержат типовые уязвимости (жёстко прописанные секреты, пароли в открытом виде) [1], [2]. Тот же набор проблем обнаружен в исследуемом стенде (раздел 3), то есть задача практическая, а не гипотетическая.
2. **Управление секретами и сертификатами — отдельная нерешённая задача.** Промышленный опыт показывает, что интеграция Vault с системами конфигурации создаёт собственные проблемы: зависимость от доступности Vault, управление токенами [12], [13]. Принципы нулевого доверия требуют взаимной аутентификации узлов [7].
3. **Платформа Kafka меняется.** Отказ от ZooKeeper в пользу KRaft [8] требует новых схем развёртывания и безопасной настройки контроллеров и брокеров, а документированных образцов на Salt почти нет.
4. **Жизненный цикл самого инструмента.** Salt поддерживается проектом Broadcom/VMware, регулярно выпускает CVE-бюллетени, ветка 3007 относится к STS, а в мае 2026 вышла 3008 LTS [9]. Нужна методика безопасного обновления и проверки состояний.
5. **Требование заказчика.** Заказчик не хотел распространять SSH-ключи на узлы. Salt позволяет работать через собственный канал master–minion, а multi-master — снижает зависимость от единственного управляющего узла.
6. **Научная новизна и практическая ценность.** По связке Salt + Vault PKI + Kafka (KRaft) мало формализованных работ [10], [11], [14]. Результатом может стать проверяемый образец с метриками, пригодный для воспроизведения.

### Цель исследования

Разработать и экспериментально проверить воспроизводимый и безопасный подход к автоматизированному развёртыванию стека Docker Swarm, K3s, PostgreSQL/TimescaleDB, Redis и Apache Kafka (KRaft) средствами SaltStack с централизованным хранением секретов и выпуском сертификатов через HashiCorp Vault.

### Задачи исследования

1. Провести аудит существующих состояний и скриптов Salt по классификации «security smells» [2] и составить перечень дефектов.
2. Спроектировать целевую архитектуру: multi-master Salt, Vault с TLS, PKI, AppRole, политики с минимальными привилегиями.
3. Реализовать единую структуру pillar/state без секретов в командных строках и открытых конфигах; настроить аутентификацию Salt в Vault без долгоживущих токенов.
4. Реализовать безопасное развёртывание Kafka (KRaft): TLS между брокерами и клиентами, защита контроллеров, выпуск и ротация сертификатов через Vault PKI.
5. Заменить cron+rsync на синхронизацию мастеров через Git и настроить CI-проверки (salt-lint, yamllint, shellcheck).
